# 第 4 周 · RAG 检索增强问答（BM25 手写实现，零第三方依赖）

把两份 Markdown 讲义做成知识库：切块 → 建索引 → 检索 top-3 → 拼上下文 → 让模型**带引用**回答；
资料不足时**拒答**。全流程不依赖向量库和 RAG 框架，只用标准库。

- 模型：`deepseek-flash`，`temperature=0`，思考模式关闭
- 语料：2 份 md，31.2 KB（`agent学习路线.md` 18.2 KB + `asyncio函数速查手册.md` 13.0 KB）
- 检索：手写 BM25（中文按「单字 + 双字 bigram」切分），加 26 个中文停用词过滤
- 评测：20 条问题（17 条可答 + 3 条语料外），**Recall@1 = 94.1%、Recall@3 = 100%、MRR = 0.961**

## 3. 工作原理

```
data/*.md
   │  chunking.parse_markdown()      按标题切段 → 超长段再切 → 每块带 doc + heading
   ▼
900+ 字符/块 × 62 块（size=512）
   │  index.tokenize()               中文单字+双字 bigram，英文数字按词
   ▼
BM25 索引（tf 表 + df 表 + 平均长度）
   │  index.search(question, top_k=3)  过滤停用词 → 打分 → 降序 → 取前 3
   ▼
3 个相关块  ──→ answer.build_context()  拼成带编号的资料
                        │
                        ▼
              llm.chat(SYSTEM_PROMPT + 资料 + 问题)
                        │
                        ▼
        带 [文件名 > 标题] 引用的答案，或「资料中没有相关内容」
```

三处关键设计：

**① 块必须带 `heading`**

```python
{"doc": "asyncio函数速查手册.md",
 "heading": "asyncio 函数速查手册 > 一、asyncio 函数总表 > 3. 等待与收集结果",
 "chunk_id": "asyncio函数速查手册#031",
 "text": "...", "chars": 510}
```

没有 `heading` 就写不出「来自文档的哪一节」，引用溯源就退化成"来自某个文件"。

**② 超长段落在自然边界断开**

```python
for sep in ("\n", "。", "！", "？", "；", ";", "，", ",", " "):
    pos = text.rfind(sep, lo, size)      # 在 [size-80, size] 里找最靠后的边界
```

初版直接 `p[:size]` 硬切，把 `Task.result` 切成 `Task.res`。改后 62 块里只剩 1 块以字母结尾（且是完整单词 `Exception`）。

**③ 查询侧过滤，而不是只靠分数**

```python
terms = [t for t in tokenize(query) if self.df.get(t, 0) > 0]   # 去掉库里没有的词
if drop_stopwords:
    terms = [t for t in terms if t not in STOPWORDS]            # 去掉 26 个中文功能词
```

不改这一步，"怎么用""我们""这个"这类词会把排序带偏（见第 6 节发现 1）。

## 4. 检索实现细节

### 分词

| 文本 | tokenize 结果 |
|---|---|
| `事件循环` | `['事','件','循','环','事件','件循','循环']`（4 单字 + 3 双字） |
| `asyncio 的 gather` | `['asyncio','的','gather']` |
| `3 次 2.5 秒` | `['3','次','2.5','秒']` |

不用 jieba 的取舍：零依赖、中文无需词典；代价是词元数变多（62 块平均 171 词元），单字噪声需要靠 IDF 和停用词压住。

### BM25 打分

```
score = Σ idf(t) · tf·(k1+1) / (tf + k1·(1-b+b·dl/avgdl))
idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))
```

参数：`k1=1.5`、`b=0.75`。实测的词元权重（N=62）：

| 词元 | df | idf |
|---|---|---|
| `asyncio` | 22 | 1.030 |
| `事件` | 7 | 2.128 |
| `部署` | 3 | 2.890 |
| `kubernetes` | 0 | 不进索引 |

### 查询分析（拒答信号）

```python
def analyze_query(self, query) -> dict:
    """known = 库里有且非停用词；missing = 库里完全没有；stopwords = 功能词"""
```

对"怎么用 Kubernetes 部署服务"返回：

```
known=['部','署','服','务','部署','服务']
missing=['么用','kubernetes','个']      ← 关键实体缺失
stopwords=['用','怎么']
```

## 5. 实验结果

### 5.1 三档 chunk 大小对比（17 条可答题）

| 配置 | 块数 | 平均长度 | Recall@1 | Recall@3 | MRR |
|---|---|---|---|---|---|
| size=256 | 108 | 185 字符 | 94.1% | 100.0% | 0.961 |
| size=512 | 62 | 285 字符 | 94.1% | 100.0% | 0.961 |
| size=1024 | 51 | 341 字符 | 94.1% | 100.0% | 0.961 |

**三档完全相同。** 原因：17 道题的答案都集中在文档的少数小节里，256 字符已足以覆盖完整小节，因此 chunk 大小在本批题目上不构成有效变量。

> 这是本实验最诚实的结论：**没有测出差异，而不是"512 最好"**。要体现 chunk 大小的影响，需要"答案跨节、需要长上下文"的题目，或结构更松散的语料（网页正文 / PDF）。

### 5.2 唯一的非满分：q13

`Recall@1 = 94.1%` = 16/17；`MRR = 0.961 = (16×1.0 + 1/3) / 17`。
唯一没排第一的是 q13「什么时候该用 LangGraph」，实际 rank=3。

### 5.3 拒答信号（3 条语料外问题）

| 题目 | top-1 分数 | 库中缺失的关键实体 | 模型行为 |
|---|---|---|---|
| q18 怎么用 Kubernetes 部署服务 | 11.51 | `kubernetes` | 拒答 ✅ |
| q19 Kafka 怎么保证消息顺序 | 17.27 | `kafka` | 拒答 ✅ |
| q20 MySQL 索引怎么优化 | 12.61 | `mysql` | 拒答 ✅ |

**注意分数：这三条"库里根本没有"的问题，BM25 分数（11.51 / 17.27 / 12.61）比不少"真能答"的题还高**（如 q01 的 6.87）。所以绝对分数不能作为拒答判据，必须用 `missing` 里的实体缺失信号 + 提示词强制拒答。

## 6. 四个关键发现

### 发现 1：停用词过滤修好了排序（对照实验）

| 查询：`asyncio 的 gather 怎么用` | top-1 | 分数 |
|---|---|---|
| 过滤前 | `agent学习路线.md`（错） | 8.43 |
| 过滤后 | `asyncio函数速查手册.md`（对） | 6.87 |

拆解 8.43 的构成发现：关键词 `asyncio`、`gather` 在那块里 **tf=0**（一次都没出现），分数全部来自 `用`(3.18)、`怎么`(3.18)、`怎`(1.29) 这类泛词。加 26 个停用词后该块分数大幅下降，专用文档浮上来。

### 发现 2：文档级召回 ≠ 答案级召回（已知局限）

`q12「第 9 周要做什么」`在文档级判为命中（命中了 `agent学习路线.md`），但实际检索结果：

```
[1] 第 7 周 · LangChain 与 LangGraph        ← 不含"第 9 周"
[2] 九、常见坑                             ← 只提到"第 9 周必须做成本看板"
[3] 第 5 周 · 记忆与状态管理                 ← 不含
```

正确小节「第 9 周 · 可观测性与工程化调试」**BM25 得分为 0 被过滤**——因为它的正文不含查询词，而**标题没有参与索引**。

模型拿到这三块后回答了「资料中没有相关内容」——**这是正确行为**（宁可拒答，不编造）。

**尝试过的修法与结果**：把 `heading` 拼进索引文本 → 第 9 周问题被召回（rank 3），但整体指标退化：

```
原索引      : R@1=94.1%  R@3=100.0%  MRR=0.961
标题入索引  : R@1=88.2%  R@3=88.2%   MRR=0.882     （q08、q13 掉出 top-3）
```

**修一个坏两个，故未采用。** 正确方向是字段加权（BM25F）或短语匹配，属于后续的检索调优。

### 发现 3：提示词优化（散文 → 要点）

初版 `SYSTEM_PROMPT` 只约束内容（只用资料 / 标引用 / 拒答），未约束输出风格。结果模型把两块**互相重复**的资料并列陈述，还自动插入"另外"等过渡词（该词在两份语料中出现 **0 次**，纯属模型生成的话语标记），读起来冗余生硬。

加入「输出格式」段后（每要点一行、禁止过渡词、重复只留一处），同一问题的回答：

| | 改前 | 改后 |
|---|---|---|
| 结构 | 3 段散文 | 2 条 `- ` 要点 |
| 过渡词"另外" | 有 | 无 |
| completion tokens | 152 | **111（-27%）** |
| 引用标注 | 3 处 | 2 处（未退化） |

**结论**：内容约束和风格约束是两类不同的东西；只写"说什么"不写"怎么说"，模型会按自己的作文习惯输出。

### 发现 4：切块边界影响引用质量

初版硬切产生 `Task.res`（`Task.result` 被截断），模型可能把半截词当专有名词，用户点开引用也看到残句。
加入"回退到最近换行/句号/空格"后：半截词块从多个降到 1 个，`size=512` 的最长块从 512 降到 510（说明确实有提前断点），检索结果不变。

## 7. 提示词与拒答设计

```text
规则：
1. 只能使用资料里的信息，不得引入外部知识，也不要凭印象补充。
2. 每个要点的末尾必须标注来源，格式：[文件名 > 标题路径]。
3. 如果资料不足以回答问题，只输出这一句：资料中没有相关内容。
4. 不要编造资料里没有的数字、名称、链接或结论。
5. 用中文回答，简洁，不超过 200 字。
6. 多份资料表达同一件事时，只保留最准确的一处，不要重复陈述。

输出格式：
- 每个要点单独一行，以「- 」开头，一个要点只讲一件事。
- 直接用要点陈述，不要写"另外""此外""同时""需要注意的是"这类过渡词。
- 要点按重要性排序，最重要的放第一条。
```

拒答有**三条路**（互为兜底）：

| 触发点 | 条件 | 实现位置 |
|---|---|---|
| 检索侧 | `search()` 返回空 | `answer.py` 第一道 if |
| 查询侧 | `analyze_query()["known"]` 为空（查询词全不在库） | `answer.py` 第二道 if |
| 模型侧 | 模型按要求输出固定拒答句 | `answer.py` 判定 `REFUSAL in text` |

## 8. 踩坑记录

| 坑 | 现象 | 原因与修法 |
|---|---|---|
| `json.load` / `json.loads` | `AttributeError: 'str' object has no attribute 'read'` | `load` 收文件对象，`loads` 收字符串 |
| `BM25(build_chunks)` 少括号 | `TypeError: 'function' object is not iterable` | 传的是 lambda，要 `build_chunks()` 调用才得到列表 |
| `writerow(all_rows)` | CSV 只有一行、内容错位 | 批量写要 `writerows` |
| `dict.key()` | `AttributeError: 'dict' object has no attribute 'key'` | 应为 `keys()` |
| `llm_config.load_dotenv()` | 报"缺少 DEEPSEEK_API_KEY" | config 模块里只有 `load_env()`；`load_dotenv` 是 dotenv 库函数，无参调用找不到 `.env` |
| `{"answe": text}` / `{"bits": hits}` | `KeyError: 'answer'` / `'hits'` | 返回字典的键名拼错 |
| `{u.get('prompt.completion_tokens', 0)}` | token 输出恒为 `+ 0` | 键名写错，`.get` 静默返回默认值 |
| docstring 里写 Windows 路径 | `SyntaxWarning: invalid escape sequence '\w'` | 用 `r"""..."""` 原始字符串 |
| 正则漏一个 `\|` | 中文完全不被分词（检索永远空） | `...\d+(?:\.\d+)?\|[\u4e00-\u9fff]+` 三个分支必须并列 |
| `properties` 拼成 `promperties` | 不报错，但模型看不到参数定义 | 数据字面量配断言校验（week03 的教训，同样适用） |

## 9. 已知局限与下一步

### 局限

1. **文档级评测掩盖了块级缺口**：`Recall@3 = 100%` 只说明"命中了正确文件"，不保证"答案所在小节进入了上下文"（见发现 2）。
2. **标题未参与索引**：靠标题才能定位的问题（"第 9 周做什么"）召不回来。
3. **语料太小**：2 份 31 KB，检索难度低；真实场景（几百份文档、长文档）表现会明显下降。
4. **无向量检索**：纯词面匹配，同义改写（"并发跑一批" vs "并发执行多个任务"）匹配不上。

### 下一步

| 优先级 | 事项 | 说明 |
|---|---|---|
| 高 | 评测升级为 **heading 级** | 给 `eval_questions.jsonl` 加 `expect_heading`，判定命中块的 heading 是否含该子串，让数字更诚实 |
| 高 | **字段加权（BM25F）** | 标题命中单独加分，而不是把标题拼进正文（后者已实测会让指标退化） |
| 中 | **短语匹配** | query 里的「第 9 周」「asyncio.gather」这类短语，块中出现时额外加分 |
| 中 | 扩大语料 | 5–10 份后再评估是否需要上述调优 |
| 低 | 向量检索 / rerank | 第 7 周框架阶段再引入；当前零依赖实现已够验证链路 |
| 低 | 结构化输出 | 让模型输出 `{"points": [...], "sources": [...]}`，彻底消灭过渡词与格式漂移 |
